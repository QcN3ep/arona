# File Service

fs places the boot archive and disk volumes into the same file tree.
When `/bin/init` is opened, the content comes from the cpio newc archive; after a persistent volume is mounted, opening `/var/log/system.log` enters ext4.
Both paths return a File session, and clients read and write through the same IPC interface, with paths and file contents transferred via page frames.

## Interface and Sessions

`Control` manages the file service and is responsible for establishing clients, mounting, and unmounting file systems.
`Client` provides path operations, and `File` and `Directory` represent opened sessions.

| Interface | Operations |
|---|---|
| Client | open file or directory, create, query metadata, make directory, delete, rename, hard link and symbolic link |
| File | read/write by offset, append, truncate, size, metadata, attribute modification, fsync |
| Directory | metadata, attributes, directory entry reading, and directory anchor for relative path operations |
| Control | connect client, mount ext4, unmount |

A synchronous client specifies an absolute deadline for a request.
The asynchronous `start_*` interfaces return a Pending object, and the caller can wait for and decode the result in an event loop.
`ReadAt` provides read-only access by offset.
init's ELF loader uses it to read the ELF header first, then locate the program headers and the contents of each segment; the data can come from either the archive view or a file session.

When opening a file, the client establishes a dedicated channel and hands over its server endpoint.
fs stores a FileSession, handles requests on that session, and releases the node and pending state after the peer closes.

## newc Archive Root

`Archive` holds the FrameAllocation handle of the boot archive and builds an ordered path index from the newc entries.
Parsing checks the header, name, data boundaries, alignment, type, and archive end marker.
File views read content by offset through the shared archive page frames.

The archive presents regular files, directories, and symbolic links, and stores metadata such as inode, permission, link count, and time.
The identity and backing data of hard link entries are resolved when building the index.
The archive root provides read-only file data, and persistent writes go to the mounted ext4 volume.

The initial contents of the root directory are determined by the archive generated by the packer.
System programs are located in `/bin`, application boot configuration is located in `/etc/init.toml`, and the persistent volume is mounted at `/var` by init.

## Path Resolution and Mounting

The Namespace combines the archive and the mount table.
For example, after ext4 is mounted at `/var`, resolving `/var/log/system.log` switches to that volume; `/bin/init` is still looked up from the archive.
When listing a directory, mount points are merged into the parent directory's entries.
A mount operation checks the target path, the relationship with already mounted paths, and disk range occupancy.

The directory anchor interface supports relative directory lookup.
The resolver handles absolute paths, relative paths, `.`, `..`, duplicate separators, and symbolic links.
An absolute target of a symbolic link is resolved from the namespace root, and a relative target continues from its parent directory.
Name length and path length are checked during processing. At most 40 symbolic links may be followed during a single path resolution.

Open options include write, create, exclusive, truncate, and permission bits.
The service performs operations according to the node type, creation conditions, and the writable state of the backend.
Cross-volume links or renames, busy mount points, and type mismatches have separate error results.

## Block Device Access

`Disk` wraps devmgr's block device Session and stores the capacity, read-only state, flush capability, and occupied volume ranges.
The file system block size is 4096 bytes.
Each disk read or write submits a request using a page frame buffer, waits for completion and ACKs, then verifies the status and actual byte count.

Disk requests carry an increasing identity.
When a request cannot be confirmed as complete, Disk stores the failure state and subsequent operations return an error.
Mounting and unmounting a volume register and release its disk range respectively.

## ext4 Disk Structure

Mounting starts from the superblock and checks the capacity, block size, feature bits, group layout, and inode size.
Currently it accepts 4096-byte blocks and 128- or 256-byte inodes, using extents and typed directory entries.
Recognized features include the internal journal, recovery flag, sparse superblock, and large file.

A volume stores block groups, block and inode bitmaps, the inode table, the block cache, and the identities of open nodes.
When looking up a file, a directory entry gives the inode, and the extent in the inode converts the file's logical blocks into disk blocks.
Reads return zeros when they encounter a hole or an unwritten extent, and a read past the end of the file completes with the actual content length.

A writable volume updates blocks and inodes through the allocator and maintains extents, directory contents, link counts, and attributes.
An open node stores the inode identity.
After a directory entry is deleted, an open file session continues to hold that node, and reclamation advances with the node reference and link state.
A valid volume without a journal is accessed through the read-only path.

## Transactions, Sync, and Recovery

Creating a file changes the directory entry, inode, and allocation bitmap at the same time.
fs stages such modified blocks in the same transaction, then writes them to the journal, and after completion updates their locations in the volume.
If operation validation fails, the staged entries are cleared; before committing, the journal capacity and device flush capability are checked.
JBD2 commit writes descriptor, data, and commit records and computes CRC32C checksums.
After committing, it syncs the device, then writes the modifications to the target blocks and syncs, and finally updates the journal state.

The volume updates the on-disk dirty and recovery state on its first modification.
`fsync` enters the volume sync path from the File session and then performs a flush through the block device.
File synchronization is carried through to the device by this service call chain.

If recovery state exists at mount time, the transactions in the journal are read and validated, and valid updates are replayed.
The orphan inode list is used to recover nodes whose link count has reached zero and to release their resources.
After recovery completes, the volume state is updated.

After an I/O error during transaction commit or sync, the volume stores the failure result and refuses further writes.
Unmounting checks open references, completes sync, updates the clean state, and releases the disk range.

## File Client Example

The following function borrows an existing file client, opens and reads the configuration:

```rust
fn read_config(
    files: &fs::Client<'_>,
    output: &mut [u8],
    deadline: u64,
) -> Result<usize, fs::Error> {
    let file = files.open("/etc/init.toml", deadline)?;
    file.read_at(0, output, deadline)
}
```

`read_at` returns the number of bytes read this time, and the end of the file can make the result shorter than the output slice.
`ReadAt::read_exact_at` keeps reading until the slice is filled or returns the corresponding error.
