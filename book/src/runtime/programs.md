# Writing Native Programs

A native program starts with `#![no_std]` and an ordinary `main`.
After linking the runtime, the program obtains a startup entry point, heap, thread-local storage, and exit handling, and then accesses kernel capabilities through typed handles.
This chapter starts with a program that returns a success status and gradually adds containers, threads, and service connections.

## Program Source File

The simplest program returns an exit status directly:

```rust
#![no_std]

extern crate runtime;

fn main() -> usize {
    0
}
```

`extern crate runtime` links in the runtime required for program startup.
The application uses Rust's `main` convention; the runtime receives the startup handoff and calls the entry point generated by the compiler.
Returning 0 indicates success.

After adding `alloc`, you can use containers and hand data to a closure thread:

```rust
#![no_std]

extern crate alloc;
extern crate runtime;

use alloc::vec::Vec;

fn main() -> Result<(), runtime::Error> {
    let values: Vec<u64> = (1..=4).collect();
    let worker = runtime::thread::spawn(move || {
        values.into_iter().sum::<u64>()
    })?;
    let _total =
        worker.join().map_err(|_| runtime::Error::Protocol)?;
    Ok(())
}
```

`move` hands `values` to the worker thread, which iterates over the four integers and returns the total 10.
The main thread waits for the result at `join`, during which other ready threads can run.
After the thread returns, the runtime obtains the result and reclaims its stack and TLS; `?` hands runtime errors to `main`'s return path, ending the program with exit code 1.

## Cargo Configuration and Linking

A native program depends on `arona-runtime`, uses `runtime` as the library name, and enables the `program` feature.
Services in the repository include it in their respective `baremetal` features, for example:

```toml
[features]
baremetal = ["runtime/program"]

[dependencies]
runtime = { package = "arona-runtime", path = "../runtime" }
```

This is the dependency style for service crates under `components/`.
Binary targets select this runtime environment with `required-features = ["baremetal"]`.

The linker script is `components/runtime/link.ld`.
It defines `_start`, organizes text, read-only data, and writable data into page-aligned `PT_LOAD` segments, and defines `PT_TLS` and the required symbols for TLS.
The program's virtual layout starts at `0x100000`.

The `build.rs` of existing services passes this script to the linker when the target system is `none`.
xtask builds services with the pinned Rust toolchain, specifying the target architecture, the `baremetal` feature, symbol stripping, and a maximum segment alignment of 4096 bytes.
See [Build and Run Workflow](../tools/workflow.md) for the build process.

## Boot Handoff and Service Requests

When the program begins execution, the runtime has already received its own Task handle and bootstrap channel from `ProcessStart`.
The service takes the channel in `main` and receives the resources delivered by the starter:

```rust
use runtime::{Error, ipc::ReceivedMessage};

fn receive_startup() -> Result<ReceivedMessage, Error> {
    let channel = runtime::process::bootstrap()
        .ok_or(runtime::Error::Protocol)?;
    channel.receive(runtime::ipc::WaitMode::Forever)
}
```

The taken channel is owned by the program; the tag, data words, and handle order of the startup message are agreed upon by the program and the starter.
For example, init obtains the startup archive and devmgr obtains the device set; they decode the message at their respective entry points and establish service state.

## Clients That Depend on Services

A service client consists of library code and a channel.
`fs`, `logger`, and `devmgr` provide Rust methods and encoding, while the startup message or other IPC delivers the corresponding service connection.

After obtaining the file service channel, the program creates a `Client`, and file operations enter the fs Task via IPC.
The log facade sends messages through the logger client, and device sessions access devices through the dedicated channel returned by devmgr.
See [Service Collaboration Model](../services/model.md) for the initialization and rights of these clients.
